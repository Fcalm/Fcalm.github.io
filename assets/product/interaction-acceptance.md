# Avery：从用户需求到交互与验收

本材料整理现有 PRD、原型和 Skill 中的设计规则，便于评审与测试；未宣称已有企业内跨部门协作经历。

## 需求切片

- 用户：需要根据目标岗位调整简历的求职者。
- 场景：已有个人经历，但每次改简历都需重新解释，且担心模型编造事实或覆盖原版本。
- 用户目标：得到一份有事实依据、可核对、能追溯版本的简历草稿。
- MVP：读取已授权档案与 JD、产出草稿、列出缺失事实、按权限确认保存。
- 范围外：自动补造经历、未经确认保存、保证面试或录用结果。

## 主流程与交互状态

用户提出目标 → 读取档案与 JD → 生成草稿 → 展示待确认项 → 用户核对 → 按当前场景权限保存 → 返回保存回执。

| 状态/触发 | 用户看到什么 | 系统处理 | 验收点 |
| --- | --- | --- | --- |
| 正在整理资料 | 当前步骤、停止入口 | 只使用已授权资料 | 不将 JD 要求当成用户经历 |
| 缺少经历或指标 | 待补充项与已有草稿 | 先询问或保留定性表达 | 不凭空增加公司、数字或证书 |
| 需要写入 | 变更范围与确认动作 | 结合聊天/工作场景与确认策略检查写入权限 | 未获授权不写入 |
| 用户拒绝/取消 | 明确的停止结果 | 保留原材料，不继续写入 | 不把拒绝当成成功 |
| 保存成功 | 可打开的材料与版本 | 检查写工具回执 | 自然语言“已保存”不能代替回执 |
| 保存失败/结果未知 | 错误原因和下一步 | 检查已有状态，避免重复写入 | 不自动扩大权限或重复提交 |

## Prompt 与交互共同约束

以下是产品级指令摘要，不是逐字生产 Prompt：

1. 明确任务：基于已确认经历与目标 JD 优化表达。
2. 明确来源：区分档案事实、用户本轮补充与岗位要求；没有事实依据时先确认。
3. 明确输出：可编辑正文、修改理由、待补充项；不要用流畅度掩盖信息缺失。
4. 明确执行边界：保存必须符合场景权限、用户意图与确认策略。
5. 明确验收：内容质量和执行完成分别检查。

验证设计：固定同一组输入、档案与模型配置，比较不同指令在事实一致性、缺失信息处理和授权行为上的表现。未取得对照结果前，不报告 Prompt 优化带来的提升。

## 用于评审与交接的最小材料

需求目标与范围、原型入口、状态矩阵、数据字段与权限、异常出口、验收案例、版本与未决问题。若多人协作，先对齐这些材料，再拆分产品/算法/研发/测试的责任；这是一份交接方案，不是已发生的团队合作业绩。
