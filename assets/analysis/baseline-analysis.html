从历史评测汇总到产品判断

分析整理：2026-10-22。样本来自项目 2026-08-28 的内部测试记录，本次没有重新运行模型。

数据与复现

  • 原始依据：Avery 评估系统开发计划，第 17.3 节。
  • CSV 汇总保留来源中的两组聚合数据，不包含用户个人资料；不是逐条测试日志。
  • Python 脚本只使用标准库，读取 CSV、检查数据范围并计算比例与单任务消耗。
  • 下载 CSV 和脚本至同一目录，运行 python analyze_baseline.py 即可复现。
指标 内容任务 浏览器执行任务

计算口径：完成率 = 完成数 / 案例数；单任务轮次和 Usage = 对应组总量 / 案例数。评分直接引用原记录，没有从均分反推明细。

这些数据支持什么决策

  1. 两类任务的原评分都高，但不能因此使用同一个质量总分。内容任务应核对事实、表达和约束；执行任务还需核对页面终态、授权与回执。
  2. 执行任务的调用轮次与 Usage 更高，应单独监测重试原因、页面状态失效、工具调用和上下文消耗。先定位消耗集中在哪一步，再决定压缩上下文或调整重试策略。
  3. 原记录提到浏览器任务有 5 次可恢复的页面引用失效。可把这一类异常单独归因，并补充恢复后的成功判据，避免重复提交。

不支持什么结论

  • 两组任务与样本量不同，不能将消耗差异解释为同一任务的效率提升或下降。
  • Token Usage 不是金额；缺少模型、输入/输出拆分及计费信息时，不计算成本收益。
  • 12 个受控测试案例不是 12 个真实用户；100% 不代表真实招聘网站成功率，也不能推导用户满意度、使用频率或留存。
  • 没有逐用例原始值，不能计算 P95、方差、显著性或构造质量趋势。

下一步的数据闭环

分别采集任务开始、完成、失败、取消、人工接管、耗时与 Usage，再结合任务后的满意度和开放反馈。按任务类型与版本分组，先看高风险失败，再看高频阻塞与体验指标。
