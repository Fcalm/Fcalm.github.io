01

从一句需求，到可跟进的求职流程

对话、档案、岗位与投递管理，组成 Avery 的日常工作空间。

01 / 对话

从一个具体任务开始

把求职需求交给 Avery，在对话中明确目标、补充上下文，再推进下一步。

  1. 提出目标说明目标岗位与要完成的任务，而不是反复切换工具。
  2. 控制执行选择聊天或工作场景，并在输入区确认当前的操作权限。
  3. 保留上下文继续已有会话，让后续工作沿用同一段任务背景。

02 / 档案

让每次生成，都有事实依据

将分散的教育、项目与工作经历整理为个人档案，作为写简历和填写申请时的资料底稿。

  1. 整理经历按教育、项目、工作、技能等类别组织资料。
  2. 确认事实点开条目核对时间、职责与成果，避免模型补写未知经历。
  3. 反复复用让同一份已确认资料服务于后续求职任务，减少重复说明。

03 / 岗位

把分散的机会，放进同一个岗位库

先保存岗位，再筛选和比较。岗位详情与来源一起保留，为后续准备材料和申请提供上下文。

  1. 收集机会通过岗位采集或手动添加，将目标机会保存到岗位库。
  2. 筛选比较按关键词、城市、求职类型等条件缩小范围。
  3. 查看依据在详情中核对岗位信息、原始链接与 JD，再决定下一步。

04 / 投递管理

投出之后，仍然知道下一步

将零散的投递结果转成可跟进的记录，用阶段和下一步日期管理持续发生的求职任务。

  1. 查看节奏在概览中了解近期投递与当前进度。
  2. 更新阶段通过已投递、笔试、面试等阶段组织投递卡片。
  3. 持续跟进从卡片查看记录与下一步日期，避免投出后失去追踪。

02

求职的痛点，发生在对话之外

起点是我自己的求职经历：重复工作占用了太多时间。

改简历、刷岗位、填网申，常常消耗一整天。我希望让求职者把精力留给学习与提升。这是产品的初始问题假设，目前尚未通过真实用户访谈或试用验证。

求职者仍要在文档、招聘网站、聊天记录和表格之间切换：找回项目经历、判断岗位、修改版本、填写申请、跟进结果。产品的切入点，是让这些步骤使用同一份可信资料。

资料重复解释

每次生成都从头开始

建立结构化档案，保存已确认的真实经历，作为后续生成的事实来源。

材料与岗位脱节

版本多，难以追溯

岗位保存完整 JD；多份简历独立管理；投递记录关联实际使用的版本。

自动化信任不足

担心填错、发错、重复投

场景限制工具范围，关键动作按权限确认，提交成功必须有可核对的证据。

当前产品重点

档案 → 简历 → 岗位 → 受控申请 → 进度跟踪。优先让核心链路稳定可用。

范围与边界

不保证获得 offer，不绕过验证码和平台风控。登录失效、信息冲突或不确定结果，需要用户接管。

03

先定义要完成的工作，再决定做哪些功能

把求职中的重复操作交给 AI，把时间留给自我提升。

第一阶段聚焦校招与实习求职者：已有个人经历，需要针对不同岗位准备材料，并持续跟进申请。产品价值应落在一段可完成、可追溯的工作上，而不是一次生成的长度。

  1. 01收集岗位保存 JD 与来源
  2. 02判断匹配对照要求与经历
  3. 03准备材料基于事实改写简历
  4. 04受控申请确认对象与操作
  5. 05跟进状态记录结果与下一步
围绕核心任务划定 MVP 范围
优先级产品选择判断依据
核心链路档案、岗位、简历与投递记录关联先减少资料重复解释和工具切换
执行前提场景权限、用户确认与结果回执错误写入或提交的代价高于少完成一步
扩展判断更多采集来源与更长的自动化任务先明确质量、成本和人工接管的边界

04

让模型提出行动，让产品约束执行

我曾考虑通用文件操作与脚本，最后选择受控工具。

面向不熟悉计算机的求职者，通用命令行与文件权限会放大误操作风险，也可能产生不必要的模型消耗。因此，我将简历修改与表单填写封装为专用能力，把可做什么、何时确认、怎样判定成功写进执行规则。

  1. 01

    明确目标与完成条件

    确认目标岗位、所用资料与任务范围。关键对象缺失时先询问，不把模糊请求直接变成外部操作。

  2. 02

    按场景选择工具与 Skill

    聊天和工作场景使用各自的工具范围。Skill 提供任务方法和内容规则，执行权限仍由工具契约控制。

  3. 03

    读取事实，推进任务

    按需读取档案、简历和 JD，区分用户事实与岗位要求；不为了满足 JD 而补造经历。

  4. 04

    在关键动作前交还控制权

    写入、上传与提交结合当前权限和确认策略处理。用户拒绝、登录失效或页面不确定时，明确停止原因。

  5. 05

    核对结果，再决定下一步

    工具回执与页面状态是执行依据。成功、部分完成、失败和未知分别表达；结果未知时先检查状态，避免重复提交。

等待补充

保留已完成部分，说明还缺什么。

用户取消

停止后续操作，明确哪些动作已发生。

结果未知

先核对证据，再选择重试或人工接管。

执行流程背后的三项取舍

为什么先建档案，再生成简历？

把事实来源与表达优化分开。

模型擅长重组与改写，但不能凭空知道用户做过什么。将已确认的经历保存为档案；缺失的硬事实先确认，再用于正式材料。

承担的代价用户需要先整理资料，因此必须通过教程和渐进录入降低门槛。

为什么区分聊天与工作场景？

让能力范围与用户意图匹配。

普通分析与外部执行的风险不同。场景固定提示词和工具范围，确认策略控制写入、上传、提交等关键节点。

承担的代价用户需要理解场景差异，产品需清晰说明当前可以做什么。

为什么不能只靠更强的 Prompt？

把规则落实到运行时。

使用工具白名单、参数校验、资源范围、确认与回执检查。模型负责提出行动，可信控制层负责约束行动。

承担的代价开发和维护成本更高，需要同时维护工具契约、权限与异常恢复。

把核心功能拆到输入、交互与验收

功能拆解 / 简历匹配与修改

不是把 JD 改写成经历，而是找到已有事实的合适表达

输入是目标 JD、当前简历和已确认的档案。先提取岗位要求，再对照经历，产出草稿、修改理由与待补充项。缺少成果数字时保留定性表达；涉及公司、证书等硬事实时，先让用户确认。

  1. 读取 JD 与档案
  2. 区分要求与事实
  3. 生成可核对草稿
  4. 确认并按权限保存
  5. 返回版本与回执

06

“回答得好”，与“做成了”分开验证

一次重要修正：高分不能掩盖任务未完成。

早期统一评分会让浏览器任务在缺少最终回执时仍拿到高分。修正后，内容任务与执行任务共用运行基础设施，但使用不同判定方式。

一次评测口径的修正

  1. 01

    发现问题：高分与未完成同时出现

    浏览器任务缺少最终回执，综合评分仍可能较高。语言解释的完整性掩盖了执行结果的不确定。

  2. 02

    定位原因：内容质量与执行状态混在一起

    语义评分能判断表达与推理，但无法单独证明页面已经提交、材料已经保存，或操作对象正确。

  3. 03

    调整方案：分开验收，硬失败单列

    内容继续看 Rubric，执行改看最终状态、结构化事件与回执。错误提交、越权上传和重复提交不被综合分抵消。

  4. 04

    形成判断：每个结论都要对应证据

    将完成状态、语义分数和硬失败分别呈现。历史基线保留其模型与样本条件；修正后的收益仍需要同条件对照验证。

内容任务 / PROMPT EVAL

语义质量看 Rubric

用 LLM Judge 评估内容，结合客观约束。结果展示维度、原因、置信度和原始输出，让分数可审查。

执行任务 / BROWSER EVAL

成功与否看最终状态

使用测试页面最终状态、结构化事件和回执确定结果。错误提交、未授权上传、重复提交属于硬失败。

产品判断

完成率、总分和硬失败分别展示。对外部操作，优先保护结果真实性，而不是追求一个漂亮的综合分数。

展开历史基线与适用范围 ＋

项目开发记录保留了 2026-08-28 的 DeepSeek 基线：Prompt 10/10 完成，平均分 98.16；浏览器 2/2 完成，平均分 97.6。

解释边界：这是特定模型、快照与测试集下的小样本历史记录。浏览器样本属于受控测试页面，不代表真实招聘网站成功率，也不是本作品集改版时重新执行的测试。

08

下一步，回到真实用户

功能完成，要落到用户任务完成

生成了简历不等于完成求职准备。资料、岗位、材料与结果需要能继续衔接。

自动化范围，要与可核验程度一起增长

权限越大，误操作与结果未知的代价越高。增加能力时也要增加确认、状态反馈和恢复路径。

内部测试之后，还要验证真实价值

评测帮助定位质量与执行问题；用户能否独立完成任务、是否愿意复用，仍需真实试用回答。

核心能力已有实现，真实使用价值仍需验证。

当前优先级是小范围试用与稳定性：观察用户是否能独立完成第一个任务，找出需要人工修正的高频路径，再评估哪些功能值得继续投入。

这段实践让我更重视验收口径：不仅定义正常流程，也定义信息不足、用户拒绝和执行结果未知时，产品应该如何结束。
